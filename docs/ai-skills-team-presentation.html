Introduction

AI agent skills

Reusable playbooks that teach assistants how we work—so output is faster, safer, and aligned with team practice.

This deck introduces what skills are, why they matter for software engineering, and how my personal set of skills packages them for Codex and Cursor.

What is a skill?

Persistent instructions, not one-off prompts

A skill is a structured document (often SKILL.md with frontmatter) that defines:

  • When to use it (description and triggers)
  • Inputs, workflow steps, validation, and artifacts
  • Safety notes and companion skills for chaining

Skills turn fragile “please remember to…” chats into versioned, shareable capability the whole team can adopt.

Self-improving skills

Local Markdown artifacts carry lessons forward

Skills can be designed to be self-improving over repeat runs: they read and update workspace Markdown files (not the installed SKILL.md itself) so context compounds in the repo you are working in. The same pattern applies to overlays—for example cli-technical-analysis sits on repository-technical-analysis for the CLI project tree (pnpm/Turbo, package scripts, CI parity) and keeps analysis artifacts consistent with the shared schema (e.g. ARTIFACTS.md).

What gets preserved

  • Follow-ups — open threads, blockers, and what to verify next
  • Possible improvements — candidates for cleanup, tests, or refactors
  • Lessons for next time — short heuristics from confirmed evidence (e.g. “when X, check Y first”), with stale notes marked when reality changes

Live data (MR threads, CI, tickets) is refreshed on each run; durable sections in artifacts such as review_mr_*.md, review_pr_*.md, and grouped-comment regions inside those files stay useful across sessions. Because they live in the same workspace tree, the agent can read them anytime—and many skills tell it to open an existing artifact first before refetching live data. For follow-on chats you can still @-mention, attach, or leave files open when you want those lessons pulled to the front of context instead of relying on search alone.

General overview

How skills fit the AI-assisted workflow

For individuals

  • Repeatable workflows without re-explaining context each session
  • Consistent commands, file paths, and review expectations

For the team

  • One source of truth in git—review and improve like code
  • Onboarding: new members inherit the same agent behavior

Skills complement IDEs and models: they shape process and quality, not raw model knowledge.

Impact

How skills accelerate software engineers

  • Shorter cycle time — Investigation, tests, and PR/MR workflows start from documented commands and repo conventions instead of improvisation.
  • Higher signal — Skills bias assistants toward evidence: reproduction steps, logs, diffs, and named artifacts.
  • Safer changes — Scoped edits, validation hooks, and explicit safety notes reduce drive-by refactors and risky automation.
  • Composable depth — Generic skills (e.g. GitLab fetch) stack with overlays (e.g. CLI-specific PR analysis) for the right level of detail per repository.
  • Parallel work — Planning and multi-agent templates make it explicit who reads, who writes, and how to merge results.
AGENTS.md

Repository constitution for agents

A root-level AGENTS.md is the repo-wide policy layer for Codex, Cursor, and anyone else automating in the tree. Prefer putting shared rules there instead of pasting the same constraints into every chat or every skill.

What it usually covers

  • Workflow gates — e.g. validate skill or docs changes, sync install paths, run agreed checks before a task counts as done
  • Contracts — how skills are named, where they live, and minimum expectations for SKILL.md (or equivalent)
  • Design principles — modularity, scoped edits, evidence-backed outputs, safe parallel work

Gap today: the CLI project and GAF repositories still do not include an AGENTS.md—adding one would align agent behavior with the same bar we use here. Example: agent-skills/AGENTS.md.

Use these for transport (GitHub, GitLab, Jira), investigation, test-first delivery, CI insight, and structured planning.

Spotlight

  • branch-change-reviewer — diff the current branch against a target (default origin/main), write a Markdown review (e.g. review_feature-branch.md), without editing code—style, architecture, tests, regressions.
  • git-rebase-conflict-resolver — rebase onto a target (default origin/main), resolve conflicts while keeping compatible intent from both sides, finish stuck rebases, then validate with the repo’s real lint, format, and test commands.
  • github-issue-triage — maintainer-facing triage after issue context is fetched with github: category, recommended next state, missing details, and clear follow-ons—not just listing comments.

Next: once investigation has narrowed scope, see plan-issues for turning analysis into an execution-ready breakdown.

Planning

After analysis: plan-issues

When repository-technical-analysis has produced enough clarity on scope and evidence, this skill picks up the story.

plan-issues decomposes the work into ordered, dependency-aware vertical slices that are ready to execute—without treating “start coding” as the only handoff.

What you get: a concise summary of the scoped change, numbered slices with purpose and separation, explicit dependencies and blockers, which slices need a human decision vs which suit an agent, a recommended execution order, pointers to sensible next skills, and (when useful) a file such as work_plan_<relevant_name>.md.

Typical follow-ups: cli-contributor to implement against the CLI overlay conventions, and tdd when each slice should ship through a test-first red-green loop. multi-spawn-agent fits when multiple workers can own disjoint slices.

Overlays

Repository-specific depth on top of core skills

An overlay is a skill scoped to one codebase or product tree. It does not replace generic skills—it narrows them: correct package managers and scripts, layout anchors, how tests map to CI, and what artifacts should look like for that repo. Use an overlay only when your checkout matches the repo it describes.

How layers stack (examples)

  • repository-technical-analysis + cli-technical-analysis — investigation with CLI monorepo repro commands and artifact shape.
  • github + github-pr-comment-analysis + cli-pr-comment-analysis — grouped GitHub PR review issues with CLI-specific verdicts and proposed fixes.
  • tdd or plan-issues + cli-contributor — delivery and validation using the CLI project’s real scripts and conventions.

Example pack: CLI project (TypeScript monorepo)

Example: understand the project structure and glue (Makefile, package.json), test execution, and use the checkout itself when responding to PR review feedback—so judgments and proposed fixes reference real files and commands, not generic boilerplate.

  • cli-contributor — implement and validate using local script conventions (not generic guesses).
  • cli-technical-analysis — narrow reproduction and analysis paths for the CLI tree; align artifacts with shared schema.
  • cli-parallel-tests — broad suites using the same shapes CI uses.
  • cli-pr-comment-analysis — GitHub PR comment grouping plus CLI-specific technical judgment and suggested responses.

The catalog also includes overlays for other repositories (same idea: core transport/workflow skill + repo pack). Prefer adding thin overlays over forking huge generic skills—shared rules stay in core or AGENTS.md.

Reuse

How can you reuse my experience

Setup and install (clone, scripts/sync_skills.sh, optional git-hooks/post-commit, env overrides like AGENT_SKILLS_SYNC_TARGETS, and how to verify your install) are spelled out in README.md—see the Install, Verify Local Setup, and Behavior sections.

  • Fork or clone agent-skills and follow README.md so your Codex/Cursor skill trees stay in sync with the manifest.
  • In the agent chat, name skills explicitly when you want a playbook applied (e.g. “use gitlab-mr-comment-analysis for MR 123” or “use github-pr-comment-analysis for PR 456”).
  • Wire overlays only in the repos they describe; keep tokens in env, not in skills or prompts.
  • Improve or fork the catalog via PR; treat each SKILL.md like shared team docs.

Feel free to contribute to the repository—fixes, new skills, and doc tweaks all help everyone. ;-)

Optional: codex-multi-agent-template/ for fixed multi-agent roles, or multi-spawn-agent for dynamic worker splits—also described from the repo root in README.md.

Secrets & auth

Store credentials locally—not in skills or prompts

Transport skills and MCP reach GitHub, GitLab, Jira, Confluence, CircleCI, and similar APIs. Authentication should live in environment variables or small local dotenv files the agent host loads—never in committed SKILL.md, team wiki, or copy-pasted chat.

Typical patterns

  • Atlassian (Jira + Confluence) — prefer authenticated acli; keep ATLASSIAN_API_TOKEN and site base URL in ~/.cursor/atlassian.env or ~/.codex/atlassian.env only for Basic-auth REST fallback.
  • GitHub / GitLab — host or CLI auth (gh, glab) or tokens in env, as documented for MCP and fallbacks.
  • CircleCI — API token in env (e.g. CIRCLE_TOKEN) for the circleci skill and MCP.
  • Project-only secrets — a gitignored .env at repo root if policy allows; do not commit it; align with your secret manager if the org requires it.

Skills assume secrets exist on the machine/session; they describe what to call, not what your password is. Prefer least privilege, rotation, and team standards over shared long-lived tokens in Slack.

Chaining skills

One short prompt, several skills

You are not limited to one skill per message. In a single prompt, spell out the workflow end-to-end and name the skills (or the capabilities they represent). The agent can run through transport steps, state changes, and analysis in order—as long as inputs, order, and expected artifacts are explicit.

What to include

  • Ordered steps — e.g. update tracker state, then investigate the repo
  • Identifiers — issue keys, branches, paths
  • Output contract — where to write the Markdown artifact (path + filename)

Example prompt

jira — transition CLI-1234 to In Progress (use our board’s valid transition).

repository-technical-analysis — in this repo, tie findings to CLI-1234 and write ./analysis_CLI-1234.md (evidence, open questions, next steps).

Jira transitions are project-specific; adjust the status name if your board uses something else. Auth for Jira stays in your env files, not in the prompt.

Plugins & extensions

Extras that pair well with skills

Skills encode workflow and conventions. MCP servers, plugins, and community packs extend what the host can reach or how it behaves—worth curating so the baseline matches how you work.

MCP servers (transport)

Model Context Protocol servers give agents structured access to external systems. Transport skills in this catalog prefer local tools and bundled helpers first (gh, glab, jira-api, …), then use MCP when local access is missing or insufficient.

Examples: github and gitlab start with gh / glab; confluence starts with authenticated acli, then Basic-auth REST helpers. Configure MCP servers your team trusts as a last-resort transport layer; workflow skills stay the same.

Caveman

JuliusBrussee/caveman is Claude Code–oriented, but also supports multiple other agents.

It makes your agent talk to you like a caveman.

Benefit: faster execution + much lower token usage.

I personally prefer the caveman dialect to the AI dialect.

Layer in editor extensions, internal tools, or other host tweaks as needed. Treat third-party plugins and packs like any dependency: read the README, know what data they touch, and prefer pinned versions or forks you trust. Keep transport (MCP) and workflow (skills) logically separate when you reason about risk.
